# Review 42: migration 22 (direct messages) — 16 Oct 2026

Branch `dm-db` (bb7fc34), built on main with review 41. On my side, on Postgres 16 with the Supabase stand-in: all migrations apply from scratch and **all 1,488 SQL checks pass** (22 files, 115 for migration 22).

**What held up:**
- **Who reads what:** only the two people, never across a block either way. Each person reads only their own `dm_members` row, so a decline, a read time and a mute never reach the other. A third person reads no thread, member, message or file.
- **Files** are read through their message: only the two people, not across a block, not once deleted, not after the reader reported it, the sender included. The sender can read their own upload only before it is sent. Upload goes only into your own folder, for a message id not used yet, within the shared daily cap. Delete is only for your own file that no live message uses.
- **Requests:** replying opens the request. A work link (joining a Space, a follow back) opens it, and it stays open when the link ends. Decline is quiet, and a new message after a decline makes it a request again. `tap_to_show` appears only on the receiver's side while unanswered. `start_dm` never shows the sender the other person's real state.
- **Spam guard:** it counts only new people who never replied, under a per-sender lock. It warns at 40 and pauses new people at 50, with the right day the pause ends. Existing threads and people with a work link are never affected. The limits are read from `app_settings`, which the app can't read.
- **Pushes:**
  - A request gives one push per new person, with no text, and none within 30 days of a decline.
  - An open thread pushes like chat: one push every 5 minutes, with the text only if the person turned it on.
  - No push when muted, declined, across a block or to a hidden account.
  - A deleted or removed message takes its text out of a push not yet sent.
  - No Activity rows.
  - The push texts are right in English and Arabic.
- **Reports and appeals** follow the Space-message pattern. The reported message is hidden for the reporter at once, and the words are kept for an appeal. A removed message's files are kept for the 14-day appeal window.
- **Grants:** every internal helper (`dm_work_link`, `dm_blocked`, `dm_preview`, `dm_post`, `dm_unanswered_count`…) is closed to the app; only the 13 functions the app needs are open. `orphan_dm_files` is service role only.
- **No counts anywhere:** an unread dot, and one Message requests row showing the newest request only.

**Verdict:** approved after R1 and R2 below. Both are small. Rerun the tests and push the branch; no recheck is needed unless a test fails.

## R1. A purged person's files show as broken in the other person's thread
The purge deletes the person's `dm-files` folder first (correct), but their `dm_attachments` rows stay. The other person's `dm_thread_page` still lists those files, so the app would show photos and voice notes that can't load. I reproduced it on the branch: after the purge test, Rakesh's page still lists a file from Omar.
- In `purge_account` (migration 22's copy), before deleting the user:
  - delete the `dm_attachments` rows of that person's messages;
  - a message of theirs with no words left gets `deleted_at = now()`, so it shows "Message deleted".
  - Their words stay for the other person, as now ("Former member").
- Test: after the purge, the other person's page lists no file from the purged person, and a photo-only message from them shows as deleted.
- Update `data-model.md` §18 (Account).

## R2. Moderation must see a reported photo, voice note or PDF
In `ops/moderation.sql` step 1, a `dm_message` shows only `body`, which is empty for a photo, a voice note or a PDF. Unwanted photos are the main abuse in private messages; that is why `tap_to_show` exists. The founder can't decide a report he can't see.
- Step 1: for `dm_message`, also list that message's file paths (`dm_attachments.storage_path`, bucket `dm-files`), so he can open them in the dashboard (Storage). Only that message's files, never the thread.
- This is an ops file, so no migration change and no test.
