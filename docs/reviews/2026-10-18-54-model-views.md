## Founder rules (don't change)
1. Drafts stay in the Navisworks file. Only published views reach the cloud, once.
2. A published view goes **only** to the Space Library as a **Model view**. It is never posted to Work, Chat or the feed automatically. People use it from the Library: attach it to a work item, or share it in chat.
3. A model view is a **light issue: title + automatic version (V1, V2…) + optional note.** No status, priority, assignee or forms ("not SaaS").
4. Deleting the viewpoint in Navisworks never deletes the published copy.

## Part A: the server (migration 27, `model-views-db`, not live)
Exactly as `model-views.md` → "Data":
- `library_files.source` + `'model_view'`;
- table `model_views` with RLS;
- `may_upload` accepts `thumb.jpg` beside `view.jpg`;
- `publish_model_view(...)` returns `(library_file_id, rev_label)`; it sets `V<n>` and supersedes the previous version;
- `my_publish_targets()`;
- `my_model_views(uuid[])`.

The **names, argument names and row shapes are fixed**: the plugin already calls them (`p_camera` and `p_comments` arrive as JSON text).

pgTAP tests, as listed in the spec:
- a non-member, or a Viewer pass, can't publish;
- a Team view stays inside its Team;
- a version only supersedes within the same viewpoint and Space/Team;
- invalid camera JSON is rejected.

## Part B: the app (Library)

  - the image (thumb);
