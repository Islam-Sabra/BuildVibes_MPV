# Review 34: migration 18 (the daybook core) — 15 Oct 2026

Branch `daybook-db` (88d22ce). On my side, on Postgres 16 with the Supabase stand-in: all migrations apply from scratch and **all 971 SQL checks pass**.

**What held up:**
- **Team privacy:** every read of a post, a work item, its events, proof photos, attachments, post files, Today and Activity goes through `can_see_space_post`. Storage reads of `posts/` and work item folders follow it too.
- **Grants:** every internal helper that takes a row (`space_post_json`, `item_needs_me`, `may_check`, `acts_for_author`, `post_has_others`, `add_post_files`, …) is closed to `anon` and `authenticated`. Only the business functions are callable.
- **Backfill and rename:** every work item gets a post with the same id; the `not_as_asked` rename is the only change to the append-only record, done with the guard off and back on. The 0.9.0 alias works.
- **Edits:** author only, Open only, locked after Done, reopened by Send back, locked after Checked, recorded in `post_edits` (append-only), owner told. Files need the files right.
- **Locks:** edit, delete and cancel lock the post first, then the work items, in the same order, so they can't deadlock each other. Cancel and check can't both land.
- **Paging:** the `(created_at, id)` cursor doesn't skip posts made at the same moment.
- **Hidden accounts** can't write to the three new tables.

**Verdict:** fix D1–D3 (and L1) in place, not live, push `daybook-db`, and I'll recheck. The decision Claude Code raised (Team items hidden from members outside the Team) is not new: it is review 33 clarification 3, already agreed. Keep it.

## Fixes (inside migration 18)
**D1. Anyone who can post can hang a work item under someone else's work item.** Confirmed on my side: Crew member C added a child under B's item.
- What goes wrong: it changes B's page without B, and because any child ends Delete (clarification 2), C can stop B from ever deleting their own post.
- Fix: in `create_work_item`, a `p_parent` must be a post the caller `acts_for_author` on (its author, or an admin when the author is gone). Walk mode and meeting notes (migration 20) make parent and children in one call, by the same person, so nothing else changes.
- Test: a non-author can't add a child; the author can; an admin can when the author has left.

**D2. An author lowered to Viewer (or with posting switched off) still checks, sends back, reassigns and cancels.** Confirmed: B, now a Viewer, checked an item.
- What goes wrong: a Viewer reads only (Daybook rule). It's also a dead end the other way: the admin can't act for them, because the author is still a member.
- Fix: treat an author who can no longer post as gone for these actions. In `author_is_gone`, add `or not public.member_can(p_space, p_author, 'create_items')`. Then `may_check`, `acts_for_author`, `item_needs_me` and the edit rule all agree: the admin acts for them, they can't.
- Tests: a lowered author can't check, send back, reassign or cancel; the admin can; when raised back to Crew, the author can again and the admin can't.

**D3. A Space's only admin who gives work to themselves can never get it checked.** Confirmed: the item stays Done for good, and the owner-is-author rule sends it to "an admin", who is the owner.
- Fix: when the author is the owner (or the author is gone), the checker is a Space admin other than the owner; **if there is none, any active Lead other than the owner.** Update `may_check` (and so Needs you) with that fallback.
- Test: sole admin raises an item to themselves, signs it done, a Lead checks it; the sole admin still can't.

**L1. Old chat cards for Team items.** Before migration 18, a Team item's card went to the Everyone thread when its owner wasn't in the Team. The card's title is now unreadable there (the item is hidden), which is right; the app must show such a card as a plain "Work item" line with no title or link, not an error. App only; add a widget test.
