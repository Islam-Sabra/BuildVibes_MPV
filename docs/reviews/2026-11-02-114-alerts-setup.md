# Review 114: alerts setup after sign-up (proposal, 2 Nov)

**Status:** approved by the founder (16:27, "ok"). Build after review 111.

## Why
- On the founder's Xiaomi (build 961), the review 113 test **Need you now** arrived as a normal notification: no drop-down, no On my way · Can't now.
- MIUI keeps a new app from waking up (Autostart off) and turns its floating notifications off. WhatsApp works only because Xiaomi allows it at the factory.
- No app can switch these settings on by itself. It can only ask, and open the exact page.
- **Founder (16:20):** "I won't know unless you tell me, so the user is the same. Like location, we should ask him to allow those settings."

## The rule
- **When:** once, right after sign-up, before the first Space. A pilot worker installs the app to join the Space, so this is minutes after install.
- **Only on phones that need it.** The app knows the phone maker (already used by "Fix it", F9).
  - Xiaomi, Redmi, POCO, Oppo, Realme, Vivo, Huawei, Honor: all four lines.
  - Samsung: Notifications and Battery.
  - Any other Android: Notifications only, so the screen is one line.
  - iOS: Notifications only (time-sensitive alerts are part of the phone's own popup).
- **The four lines,** each with one button that opens its page:
  1. **Notifications:** the phone's own popup (Android 13+). A tick once allowed.
  2. **Autostart:** opens the maker's Autostart page; the app's own page if that fails.
  3. **Floating notifications:** opens the app's notification settings, on the Need you now category.
  4. **Battery: No restrictions:** opens the app's battery page. No `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` popup (Google Play policy).
- **Ticks:** a line shows "On" only where the phone can confirm it: notifications allowed, the channel's importance, battery optimisation off. For Autostart and floating notifications, which no phone reports, the line shows "On" after the person has come back from that page, and the test is the real proof.
- **Send me a test:** the server sends this person one `need_you_test` push on the strong channel. When the app sees it arrive, the line "The test arrived. Urgent alerts will reach you." shows and Done appears (PS2).
- **Later:** skips. Nothing is blocked.
- **Asked again, once (PS3):** when an urgent push (Need you now, a check-in opening) is opened more than 5 minutes after it was sent, and a line is still off, a sheet opens once: "An urgent alert arrived late". Fix now opens PS1. It never shows again after that.
- **Settings → Notifications → Fix it** (F9) opens the same screen, so there's one place for it.
- **Location is not here.** It stays asked at the first check-in.

## Bugs from the founder's test of build 961 (2 Nov, 16:47–16:49)
- **B1. Stuck in a Space after Discard.**
  - **What he did:** tapped "needs you" → a Space opened on a draft post → **Discard** → **Back**. The Space came back at once, every time. Closing and reopening the app fixed it.
  - **The lead's reading so far (code only, not reproduced):**
    - The path is Spaces tab → `/needs` (push) → `/spaces/:id?card=…` (push).
    - Back in the Space goes through two `PopScope`s in `daybook_tab.dart` (the composer's, which always holds Back, and the Work tab's, `canPop: !_writing && !selecting`) and then `space_screen._back()`.
    - `_discardDraft()` calls `discard()` and then `_stopWriting()`. `_stopWriting()` calls `close()` on a draft that was just discarded.
    - Something reopens the Space or the composer on each Back. Suspects:
      - a draft listener that opens the composer when a draft exists;
      - the `?card=` target being acted on again on rebuild;
      - `_back()` falling to `context.go(home)` while Home redirects back.
  - **Fix process (superpowers:systematic-debugging):**
    1. Reproduce on the emulator from both the Needs-you line and a push.
    2. Log the route stack and `_writing` on each Back.
    3. Write a widget test that fails, then fix the root cause.
- **B1, the lead's trace after the founder's answer (17:19: it started from a notification, not the Needs-you line):**
  - Two hosts open a Space with `go`, not `push`:
    - `NeedYouHost._tapped` (`need_you_phone.dart:225`);
    - `CheckInHost` (`check_in_phone.dart:368`).
  - `go` to a root-level route takes the tabs' shell (`AppShell`) off the stack, and with it every host: `PushHost`, `CheckInHost`, `NeedYouHost` and the reminder hosts.
  - In the Space, Back finds nothing to pop, so `space_screen._back()` calls `context.go(home)`. That builds a new `AppShell` with new hosts.
  - The new `PushHost._start()` calls `initialTap()` again (`getInitialMessage()`), and the reminder hosts call `launchedBy()` again. Both still answer with the notification that launched the app, so the Space opens again. This is the loop; killing the app ends it.
  - Today's other candidate notification is the **check-in nudge** (cron since 13:15 UTC), which opens the composer filled from the last check-in, a draft. That matches "a Space on a draft".
  - **Hypothesis to confirm first:** a launch tap is applied again each time the shell is rebuilt.
  - **Reproduce on the emulator:**
    1. Kill the app.
    2. Send Test Lead a `need_you` (or `check_in_nudge`) push.
    3. Open the app by tapping it.
    4. Press Back twice.
  - **Failing test first:**
    - mount `AppShell` twice with the same fake `initialTap()`, and expect the Space to open once;
    - from a `need_you` tap, Back reaches the Spaces tab.
  - **Fix the root:**
    - the launch tap and `launchedBy()` are taken **once per app start**: kept in a provider and cleared when used;
    - the hosts open a Space with `push` (as `openRoute` does), so Back returns to the tabs.
- **B2. The app uses 1.25 GB on the phone.** The founder's split (17:00): App size **85.77 MB**, User data **1.17 GB**, Cache **1.17 GB**. MIUI counts the cache inside user data, so almost all of it is the app's **cache folder**.
  - **The phone is kept as it is** until it has been measured: the founder doesn't clear the cache, so the files can be listed.
  - **The lead's leading guess:** copies of picked files that are never deleted. `file_picker` and `image_picker` copy each pick into the app's cache. `photo_privacy.dart` writes into `Documents/cleaned`. The outboxes keep files in `Documents/outbox` and `chat_outbox`.
  - **Before fixing,** measure with `adb shell run-as` and `du` on `cache/`, `files/` and `app_flutter/`.
  - **Then:**
    - delete each copy once its upload is done;
    - clear `cleaned/` and picker copies older than a day at app start;
    - cap any image cache.
    - No "Clear cache" setting (rule 7).
- **B3. Background work drains the battery** (founder's phone, 16:59, charging since the last full charge):
  - CPU total 7m 48s, foreground 2m 36s, so **about 5m 12s in the background**;
  - Keep awake 1m 53s;
  - GPS 5s;
  - battery set to No restrictions.
  - **Reading:** the app keeps working when it isn't on screen: realtime channels, refetches on their events, periodic timers. On a worker's phone in a pocket all day, that drains the battery and gets the app killed by MIUI, which also breaks urgent alerts.
  - **Measure first:**
    - `adb shell dumpsys batterystats --reset`;
    - an hour with the app in the background (not swiped away);
    - then `dumpsys batterystats com.buildvibes.buildvibes` for wakelocks, jobs, alarms and CPU;
    - plus a debug log of which providers, timers and channels are alive while paused.
  - **Fix after measuring:**
    - On `AppLifecycleState.paused`/`hidden`, close realtime channels and stop periodic timers.
    - On `resumed`, refresh once and reopen them.
    - Urgent things keep arriving by push, as now.
    - Check that the FCM background handler does only what a push needs and returns.
  - **Test:** with the app paused, no timer fires and no channel is subscribed; on resume, one refresh.

### B1 confirmed on the emulator (Cursor, 17:36)
- **Reproduced:** a `need_you` notification from the founder → the app killed → opened by its tap → the Space's ← arrow loops: `canPop=false` → `go(home)` → new shell → the Space again, every time. The Android system Back closes the app.

  2. `NeedYouHost` and `CheckInHost` open a Space with `push` (as `openRoute` does).
     - The test: from each tap, the Space's ← arrow reaches the Spaces tab.

### B2 measured and traced (3 Nov, build 987, the storage log)
- **The log, 08:58:34:**
  - `cache` 1,166,249,964 bytes; `files` 3 KB; `app_flutter` 224 KB (outbox 205 KB, chat_outbox 24 KB).
  - **1,136,104,986 bytes sit directly in `cache/`.** The top 20 files are all `.pdf` of 9,131,772 bytes: about **124 copies of one 9.1 MB PDF**.
  - `cache/file_picker/` holds only 3 copies (27 MB).
- **Root cause (the lead, from the code):**
  - `pdfx` 2.11 `PdfDocument.openData(bytes)` on Android writes the bytes to `cacheDir/<random>.pdf` (`Messages.kt` `openDataDocument`) and **never deletes it**.
  - We call `openData` in two places:
    - `file_preview_screen.dart:252`, the full preview;
    - `daybook_photos.dart:35`, `filePreviewProvider`, the first-page picture on every PDF file card.
  - `filePreviewProvider` is `autoDispose`. Every time a PDF card comes back on screen, the app **downloads the whole PDF again** and leaves one more copy in the cache.
  - So scrolling the Daybook costs storage and, on site, **mobile data** (9 MB each time).
- **Fix, test first (the lead's call):**
  1. **One local copy per file:** a small file cache in `lib/core/`. A storage path (it never changes for a version) maps to `cache/bv_files/<hash>.<ext>`. It downloads once, and every later open uses the local file.
  2. **Never `openData` again.** Use `PdfDocument.openFile(localPath)`, which doesn't copy. A test or a lint check that `openData` isn't used in `lib/`.
  3. **The card's first-page picture is kept on disk** (`cache/bv_thumbs/<hash>.png`). A card shown again never downloads or renders again.
  4. **A cap:** `bv_files` plus `bv_thumbs` stay under **200 MB**. At app start, the least recently used files go first.
  5. **Clean-up at app start:**
     - delete the leftover `*.pdf` files directly in `cache/` (pdfx's, never ours);
     - delete `cache/file_picker/*` older than a day, unless a pending outbox item points at it;
     - delete `cache/share_plus/*` older than a day.
  6. **Tests:**
     - the same path twice → one download;
     - the cap evicts the oldest;
     - the clean-up removes the pdfx leftovers and old picker copies, and keeps an outbox file;
     - the provider opens with `openFile`.
- **Phone check:** after the next build, open the app (the clean-up runs), open a Library PDF 3 times and scroll a Daybook with a PDF card up and down. Then read the storage log again: `cache/` is small, and the 9 MB PDF is there once.
