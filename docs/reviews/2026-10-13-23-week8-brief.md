## 2. Safety (part 1, migration 15 `safety`)
**Tables:**
- `reports`:
  - `id`, `reporter_id`, `target_kind` ('post' | 'reply' | 'profile' | 'message'), `target_id`;
  - `reason` (the six R1 reasons as ids), `note` (at most 500 characters, needed for "Something else");
  - `status` ('open' | 'removed' | 'dismissed'), `created_at`, `decided_at`.
  - Unique per reporter and target.
  - Port the shape of the old app's report migrations, rewritten to this repo's rules.
- `content_removals`: `id`, `target_kind`, `target_id`, `author_id`, `reason`, `report_id`, `removed_at`, `appeal_note`, `appeal_at`, `appeal_status` ('none' | 'open' | 'upheld' | 'reversed').

**Functions:**
- `report(kind, id, reason, note)`:
  - The reporter must be able to see the target (a post they can read, a message in a thread they can use).
  - Never your own content.
  - At most 20 a day.
  - The reported post, reply or message is **hidden for the reporter at once**.
  - The reported person is never told who reported.
- `block(person, on)`: uses the existing `blocks` table. Every block rule already enforced on the server keeps working; add tests that blocking from the new UI hides posts, replies, profile and Activity both ways.
- **Service role only, through an `supabase/ops/` script the founder or Claude Code runs on request:**
  - `decide_report(id, 'remove' | 'dismiss', reason)`. Remove soft-deletes the post, reply or message (as its author's delete does), writes a `content_removals` row, and sends the author an Activity row `content_removed`.
  - `decide_appeal(id, 'uphold' | 'reverse')`. Reverse restores the content. The result goes to Activity.
- `appeal(removal_id, note)`: the author only, once, within 14 days, at most 500 characters.
- **Moderation alert:** a trigger on a new `reports` row calls a small Edge Function `report-alert` (the same Vault and `pg_net` pattern as push). It emails the market's moderation address through Resend.
  - The moderation address is a **market pack field** (`markets.moderation_email`), not code.
  - The email holds only the report id, kind, reason and a link to the ops script. It never quotes the content.

**Screens:**
- The report sheet (R1) from: the post `•••` (someone else's post), the reply `•••` (someone else's reply), the person profile `•••`, and the Space chat message sheet (S8c, "Report message").
- R2 "Report sent", with **Block this account** for posts and people.
- The block dialog and toast (Overlay · Block dialog, Toast · Blocked) on the person profile `•••`.
- S7 Blocked accounts, with Unblock. Your own count of blocked accounts is allowed (rules §2).
- R3 removed notice, opened from the Activity row; then R4 appeal and R5 received.
  - **Wording change:** the prototype says "A different reviewer will look at it". The pilot has one reviewer, so the copy says "We'll look at it again." Arabic: "سنراجعه مرة أخرى."
  - Nothing may promise what we can't do.

**Tests:**
- you can't report your own content or something you can't see;
- reported content is hidden for the reporter only;
- the reported person can't read reports;
- only the service role can decide;
- an appeal works once, by the author only, within 14 days;
- a removal hides the content for everyone except its author's R3 notice.

## 3. Account (part 2, migration 16 `account`)
**Deletion** (founder decision, 4 Oct): the profile is hidden at once, the person can restore it within 30 days, then it's gone for good.
- `request_account_deletion()`:
  - Refused while the person is the **only admin of a Space with other active members**: S12b lists those Spaces, each with Transfer ownership (S15d).
  - Otherwise it sets `profiles.deletion_scheduled_at = now()` and signs out every phone (removes push tokens).
- **Confirmation (S13):** a 6-digit code to the person's email, with the existing sign-in code flow (reauthenticate), never a password. Copy: "Enter the code we sent to {email}."
- **While hidden:**
  - The profile, posts, replies, follows and shown work disappear for everyone else, and the person drops out of people search.
  - In Spaces, their name shows as "Former member" / "عضو سابق". If they restore, it comes back.
- **Restore:** signing in during the 30 days shows S14 with **Restore my account**, which clears the date.
- **`purge_deleted_accounts()`**, service role only, daily (an `supabase/ops/` cron script; a live change):
  - Deletes the auth user after 30 days. Profiles, posts, replies, follows, CV, push tokens and notifications cascade.
  - Space records already `set null`, so work items, messages and Library files stay as "Former member".
  - Deletes their avatar and post photos from storage. Space photos stay; they belong to the Space.
  - Runs the existing last-admin handover first.
- **Download my data (S10, S11):**
  - "Request my data" writes a `data_requests` row and shows S11.
  - An `supabase/ops/export_my_data.sql` script produces a JSON file per request, which the founder sends.
  - At most one open request per person.

**Settings (S1 v2, MVP form):**
1. **"Your settings, in words"** lines, generated from the real settings:
   - Privacy: "{n} blocked accounts" or "Nobody blocked".
   - Notifications: the three switches in words.
   - Language: "{language}. The week starts on {weekday}, in {city} time.", all from the pack.
2. **Account:** Account and security (S2: Download my data, Delete account).
3. **Privacy and safety** (S5): only Blocked accounts, plus a note that work items, chat and Library stay inside each Space.
4. **Language and region** (S8):
   - App language (English / العربية, one single-choice control);
   - Country: the home market, one single-choice list of **live** markets.
   - The week start and time format show as read-only lines from the pack; they aren't settings.
5. **Support:** Help and feedback (the support email from the pack), About BuildVibes and legal (the Terms and Privacy links from `markets.legal`).
6. **Sign out** with the S15 dialog. The copy says "You'll need a code sent to your email to sign in again"; there are no passwords.

## 4. Translate (part 3, migration 17 `translate` and Edge Function `translate`)
**The founder sets up** (steps in §7):
- a Google Cloud project with billing, the Cloud Translation API, and an API key restricted to that API;
- a $10 budget alert;
- the key goes only into Supabase secrets as `GOOGLE_TRANSLATE_API_KEY`.

**Server:**
- `post_translations`: `post_id`, `lang`, `body`, `created_at`. Service role writes only.
- Edge Function `translate` (signed-in users, `verify_jwt` on), input `{post_id, target}`:
  - Read the post **with the caller's own token**, so blocks, mutes and deletes still apply.
  - Use the cache if it is newer than the post's `edited_at`. Otherwise call Google Cloud Translation (Basic, v2), store and return.
  - At most 100 new translations per person per day. Only 'en' and 'ar'.
  - Never log the text.

**App (L1–L4):**
- "Translate" under a post whose language differs from the app language.
- After: "Translated from Arabic · Show original" (the L4 frame).
- Arabic copy: "ترجمة"، "مترجم من الإنجليزية · عرض الأصل".
- The translation keeps its own text direction.
- **Failure:** "Couldn't translate. Try again." The original stays.
