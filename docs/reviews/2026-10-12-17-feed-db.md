# Review 17: migration 12 (feed) — 12 Oct 2026

Branch `feed-db` (cc695cb). All 495 SQL checks pass on my side.

An independent review probed the migration as signed-in users. It found no way to:
- read across a block, in either direction;
- read deleted posts, or other people's Useful marks or mutes;
- write to the tables directly, or upload into someone else's folder.

Nothing is open to `anon`, and the earlier Space storage functions are untouched.

**Verdict:** passes after the fixes below. Migration 12 isn't live, so fix it **in place** (same file), add the tests, and push `feed-db` again for a quick recheck. Then ask the founder's yes to put it live.

## A. Fix before it goes live
1. **One level of replies isn't enforced.** A reply to a reply-of-a-reply is accepted today.
   - In `add_reply`, require the target to be a top-level reply: `r.reply_to is null` in the `p_reply_to` check.
   - **App (H17):** replying to a second-level reply stores the top-level reply as `reply_to`. The composer still shows "Replying to {name}" for the person you tapped. In the list, replies sit under their top-level reply, oldest first.
   - Test: a reply to a second-level reply is refused.
2. **Post photos are never cleaned up, and the author can't remove them.**
   - **(a) Delete policy** on `post-media`: the owner may delete their own object when no `post_media` row points to it. Use a `security definer` helper for the check.
   - **(b) `orphan_post_media(p_age)`**, service role only. It claims:
     - objects with no `post_media` row, older than `greatest(p_age, interval '1 day')`, so photos still in the outbox survive;
     - photos of posts deleted more than 30 days ago (kept that long for the week 8 appeal window).
     - Use the same `file_cleanup_claims` flow as Space files. It runs in the nightly cleanup, which is still waiting for the founder's yes.
   - **(c) Daily cap:** 100 MB of post photos per person per day, in `may_upload_post_media`, next to the 100-file cap.
3. **`posts_tagged` scans every post** (about 1 s at 200,000 posts).
   - Filter by `p.project_id in (select id from projects where id = p_project or merged_into = p_project)` first, so `posts_project_idx` is used.
4. **The upload check scans the whole bucket** (about 125 ms per photo at 100,000 objects).
   - Use the folder prefix range from review 11: `o.name collate "C" >= me || '/' and o.name collate "C" < me || '0'`.
5. **Rate limits can be beaten with parallel calls.** 10 parallel `create_post` calls at 19 posts made 29.
   - Take `pg_advisory_xact_lock(hashtextextended('post:' || me, 0))` before counting. Do the same with `'reply:'` in `add_reply`.
6. **The image check is loose.** A file with no type, or `image/svg+xml`, passes. The path accepts `notauuid/evil.exe` and an empty file name.
   - In `create_post`: the type must be one of `image/jpeg`, `image/png`, `image/webp`, `image/heic`.
   - In `may_upload_post_media`: the post folder must be a uuid, and the file name must end `.jpg`, `.jpeg`, `.png`, `.webp` or `.heic`, as the Space photo rule does.
   - Test: other person's folder, bad path, wrong type.

## B. Small, also in place
7. **No home market:** run the home section only when the viewer has a home market, and use `p.market_id = v_market`, which also uses the index. Today, people with no market get a "home" section of other people with no market.
8. **The 30-day window moves while scrolling,** so a post can show twice. Put `since` in the cursor and return it from `feed_page`.
9. **A two-step merge drops the tag** (A → B → C). `shown_project` should follow the chain to the end, at most 5 steps.
10. **Add the test** that a post author doesn't see a reply from someone they blocked. The behaviour is already right.

## C. Accepted
- **Following people one at a time could show who marked a post Useful.** That's what the proof line does by design (names of people you follow). No change.
